# TENSA Engineering Website Information Architecture

## Purpose

This document defines the information architecture for the TENSA Engineering website.

TENSA Engineering is the umbrella engineering company and public brand behind a controlled-AI ecosystem. The website is the long-term public home, knowledge hub, and future product funnel for that ecosystem.

The site should be designed to grow over time without needing major restructuring.

It should organize public-facing information around:

- NeuroCore
- Argus ACLI
- Argus Lab
- controlled AI systems
- local-first AI
- persistent AI memory
- AI operations
- safe AI tool interaction
- Linux diagnostics
- real-system troubleshooting
- glossary / term reference
- AI-assisted systems engineering

The goal is not to create a small temporary single-page site.

The goal is to build a serious public knowledge hub that teaches, builds trust, explains the ecosystem, proves the philosophy, and eventually supports product adoption.

## Brand Philosophy

The origin story matters.

NeuroCore began with a continuity failure:

An AI forgot the project it was helping build.

That failure exposed the core lesson:

    Intelligence without continuity is fragile.

From that came the need for:

- persistent context
- long-term memory direction
- repository-grounded source-of-truth documentation
- build logs
- architecture maps
- resume prompts
- mid-build continuity procedures
- anti-drift safeguards
- controlled execution
- structured system interaction

The public story should make clear that NeuroCore did not begin as an abstract AI governance project.

It began as a practical continuity problem.

The control-plane architecture emerged because persistent AI that interacts with real systems needs boundaries, auditability, tool control, memory control, and safe execution.

Important distinction:

    Control was not the original vision.

    Control is what the original vision required once AI began interacting with real systems.

## NeuroCore Page Strategy

NeuroCore should be presented as the platform layer.

Core message:

    NeuroCore is a local-first AI platform for persistent understanding, controlled tool interaction, and real-system awareness.

Key concepts:

- persistent daemon architecture
- runtime manager
- control plane
- execution engine
- tool registry
- system tools
- Argus tool layer
- structured output contracts
- observability and tracing
- memory and continuity direction
- reasoning/model path
- governed execution

Do not reduce NeuroCore to only AI governance.

Governance is part of the architecture.

The deeper purpose is persistent local understanding with controlled real-system interaction.

---

## Argus ACLI Page Strategy

Argus ACLI should be presented as the first practical product/distribution built on NeuroCore.

Core message:

    Argus ACLI is a read-only Linux system intelligence tool that helps users understand system state quickly, clearly, and reliably.

Key concepts:

- read-only diagnostics
- local-first execution
- real telemetry
- structured findings
- severity classification
- recommendations
- raw evidence
- concise output
- raw mode
- summary mode
- JSON mode
- severity filtering
- signal filtering
- command-name-aware behavior

Argus ACLI should be explained as practical, useful, and trust-focused.

It does not:

- modify system state
- restart services
- change configuration
- execute fixes
- automate remediation

It inspects, structures, and explains.

---

## Argus Lab Page Strategy

Argus Lab should be presented as an early real-Linux troubleshooting, training, and validation implementation with a larger future platform direction.

Core message:

    Argus Lab is a real-Linux troubleshooting and validation environment built around controlled failures, resettable scenarios, and progressive AI-guided learning.

Key concepts:

- real Linux systems
- controlled fault scenarios
- resettable lab sessions
- realistic troubleshooting
- mentor-style guidance
- adaptive difficulty
- validation of NeuroCore
- validation of Argus ACLI
- regression testing for diagnostic intelligence
- future skill tracking and proficiency levels

Argus Lab must be clearly labeled as early implementation.

It should not be marketed as publicly available, downloadable, or a finished training product until that is true.

## Repository Boundary Rules

The GitHub repositories remain the source of truth.

The website should not replace the repos.

The website should translate, organize, and explain.

### TENSA Website

Responsible for:

- public explanation
- ecosystem navigation
- educational content
- SEO articles
- product positioning
- trust-building
- conversion
- linking to source proof

### NeuroCore Repository

Responsible for:

- implementation source of truth
- architecture docs
- build logs
- source code
- technical history
- detailed system design
- active development records

### Argus Lab Repository

Responsible for:

- lab architecture
- scenario design
- validation strategy
- future training platform planning
- implementation when phase begins

### TENSA Website Should Not

- duplicate entire technical docs
- become a raw build-log mirror
- expose every internal planning detail
- overstate current product maturity
- bury visitors in architecture too early

### GitHub Repositories Should Not

- be expected to sell the product
- be expected to teach every beginner concept
- replace public website explanations
- carry the full burden of SEO or branding
