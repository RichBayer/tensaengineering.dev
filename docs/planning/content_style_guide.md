# TENSA Engineering Content Style Guide

---

## Purpose

This document defines the public writing style for the TENSA Engineering website.

TENSA Engineering is the umbrella engineering company, public brand, and ecosystem owner behind NeuroCore, Argus ACLI, Argus Lab, and the public Knowledge Base.

The TENSA website is the public home for that ecosystem.

The Knowledge Base is the public teaching and explanation layer.

NeuroCore is the platform foundation inside the TENSA ecosystem; it should not be framed as the thing TENSA exists only to explain.

The site should explain:

- TENSA Engineering
- NeuroCore
- Argus ACLI
- Argus Lab
- controlled AI systems
- local-first AI
- persistent AI memory
- AI operations
- safe tool interaction
- Linux diagnostics
- troubleshooting training

The goal is to make public pages clear, credible, useful, and technically honest without sounding like corporate marketing, internal planning notes, or AI hype.

This is an internal planning document.

It is not a public website page.

---

## Core Principle

Write like a serious builder explaining real systems to intelligent readers.

The public site should feel:

- practical
- grounded
- technically credible
- readable
- human
- honest about current progress
- confident without hype
- educational without talking down to the reader

TENSA Engineering should not sound like a generic AI startup.

It should sound like a real engineering project with a clear philosophy, real implementation work, and a disciplined approach to AI-assisted systems.

---

## Public Writing Goals

Public pages should help readers understand:

1. What the thing is.
2. Why it exists.
3. What problem it solves.
4. What exists now.
5. What is still being built.
6. How it fits into the larger ecosystem.
7. Where to go next for deeper explanation or proof.

Every page should move the reader forward.

Do not dump everything onto one page.

Use the website structure intentionally:

- Homepage introduces.
- Project pages explain major systems.
- Knowledge Base pages teach concepts.
- Story pages explain origin and philosophy.
- Build Notes summarize development milestones.
- Resources collect links and future user actions.
- Approved public artifacts provide proof where appropriate; private implementation repositories remain engineering source of truth rather than default public links.

---

## Voice

Use a voice that is:

- professional
- direct
- builder-focused
- practical
- plainspoken
- technically serious
- mildly conversational when helpful

The tone should feel like:

    A capable engineer explaining a real system clearly.

Not:

    A startup pitch deck.
    A corporate brochure.
    A hype-heavy AI product page.
    A raw internal design note.
    A textbook.
    A Reddit rant.
    A sales funnel pretending to be documentation.

---

## Preferred Style

Prefer:

    Clear explanation.
    Grounded claims.
    Plain English before jargon.
    Honest current-vs-future distinction.
    Strong topic structure.
    Short paragraphs.
    Useful examples.
    Natural internal links.
    Proof where appropriate.

Avoid:

    Over-compressed marketing blurbs.
    Buzzword stacking.
    Long walls of architecture jargon.
    Claiming more maturity than exists.
    Saying future features are available now.
    Explaining every internal implementation detail too early.
    Turning the homepage into an encyclopedia.
    Turning public pages into internal planning documents.

---

## Hype Filter

Avoid phrases like:

- revolutionary
- game-changing
- industry-leading
- next-generation
- cutting-edge
- disruptive
- autonomous AI agent
- fully automated infrastructure
- self-healing system
- production-ready
- enterprise-grade
- AI-powered everything
- unlock productivity
- seamless transformation

Use stronger, more grounded alternatives:

| Avoid | Prefer |
|---|---|
| Revolutionary AI platform | Controlled AI system for real environments |
| Autonomous agent | Governed tool interaction |
| Self-healing infrastructure | Diagnostic support and evidence-backed recommendations |
| Enterprise-grade | Designed around control, traceability, and local-first operation |
| AI-powered diagnostics | Structured Linux system intelligence |
| Fully automated fixes | Read-only diagnostics and human-directed troubleshooting |
| Next-generation AI memory | Engineered continuity and repository-grounded context |
| Seamless productivity | Less guessing, more signal |

## Current-vs-Future Language

Always distinguish between:

    What exists now
    What is being built
    What is planned
    What is long-term vision

This is especially important for:

- Argus ACLI
- Argus Lab
- install/download guidance
- product maturity
- commercial offerings
- training platform features
- proficiency tracking
- model-guided troubleshooting
- future automation
- hosted services

---

## Current Reality Wording

Use wording like:

- currently
- today
- in the current version
- the current public site
- the current V1 direction
- the current implementation focuses on
- the initial version is designed to
- this page currently introduces
- the current foundation includes

Example:

    The current Argus ACLI direction is read-only by design. It focuses on inspecting Linux system state, preserving raw evidence, and turning system signals into structured findings.

---

## Future-Phase Wording

Use wording like:

- planned
- future-phase
- intended
- the long-term direction
- the roadmap includes
- the system is being designed to support
- future versions may
- this is not currently available
- this should not be treated as a released feature

Example:

    Argus Lab is a future-phase training and validation environment. It is intended to use real Linux systems, controlled faults, resettable scenarios, and mentor-style guidance, but it should not be presented as currently available.

---

## Avoid False Maturity

Do not say:

    Argus ACLI provides production-ready Linux diagnostics.

Prefer:

    Argus ACLI is being built as a read-only Linux diagnostics tool that turns real system telemetry into structured findings, recommendations, severity, and raw evidence.

Do not say:

    Argus Lab trains users through live troubleshooting sessions.

Prefer:

    Argus Lab is planned as a real-Linux troubleshooting and validation environment where users will eventually work through controlled failure scenarios.

Do not say:

    NeuroCore safely executes system changes.

Prefer:

    NeuroCore separates reasoning from authority and routes tool interaction through governed execution paths. Argus V1 is read-only by design.

## Project Positioning Rules

### TENSA Engineering

Describe TENSA Engineering as:

    the public hub, knowledge platform, and ecosystem portal for NeuroCore, Argus ACLI, and Argus Lab.

TENSA Engineering should be framed around:

- controlled AI systems
- local-first AI
- operational continuity
- safe tool interaction
- public education
- ecosystem organization
- source-grounded engineering proof and approved public artifacts

Avoid making TENSA sound like a generic consulting company unless that becomes an explicit direction later.

---

### NeuroCore

Describe NeuroCore as:

    a local-first AI platform for persistent understanding, controlled tool interaction, and real-system awareness.

Core ideas:

- persistent local understanding
- continuity
- controlled execution
- governed tool interaction
- daemon-based runtime
- control plane
- structured system interaction
- observability
- local-first direction
- foundation for Argus ACLI and Argus Lab

Do not reduce NeuroCore to only AI governance.

Governance is part of the architecture.

The deeper purpose is persistent local understanding with controlled interaction against real systems.

---

### Argus ACLI

Describe Argus ACLI as:

    the first practical product or distribution built on NeuroCore.

Core ideas:

- read-only Linux diagnostics
- local-first operation
- real telemetry
- structured findings
- severity classification
- recommendations
- raw evidence
- concise output
- optional raw/summary/JSON output modes
- practical troubleshooting support

Argus ACLI does not:

- modify system state
- restart services
- change configuration
- execute fixes
- automate remediation
- replace human judgment

Preferred phrasing:

    Argus ACLI inspects, structures, and explains. It does not apply fixes.

---

### Argus Lab

Describe Argus Lab as:

    a future real-Linux troubleshooting, training, and validation environment.

Core ideas:

- real Linux systems
- controlled failure scenarios
- resettable lab sessions
- troubleshooting practice
- mentor-style guidance
- validation environment for Argus ACLI
- future skill tracking
- demonstrated troubleshooting ability

Argus Lab should not sound like:

- a quiz app
- a fake terminal simulator
- a simple tutorial site
- a finished product

Preferred phrasing:

    Real skill comes from solving real problems.

## Story Style

The origin story matters, but it should stay professional.

The story should explain:

    An AI forgot the project.
    That exposed the fragility of intelligence without continuity.
    Documentation became external memory.
    Structured workflows reduced drift.
    Local AI suggested persistent understanding.
    Real system interaction required governance.
    NeuroCore emerged.
    Argus became the first practical proof.
    Argus Lab became the future training and validation environment.

Story pages should be:

- human
- honest
- memorable
- grounded
- technically connected
- not melodramatic
- not over-polished

Avoid turning the origin story into startup mythology.

It should feel real because it is real.

---

## Technical Explanation Pattern

When introducing technical concepts, use this pattern:

1. Plain-English explanation.
2. Technical term.
3. Why it matters.
4. How it applies to NeuroCore, Argus, or Argus Lab.
5. Link to deeper explanation if one exists.

Example structure:

    Raw command output can show what happened, but it does not always explain what matters.

    Argus ACLI is designed to preserve that raw evidence while also turning it into structured diagnostic findings.

    That distinction matters because a user should be able to see both the interpretation and the underlying system signal that supports it.

---

## Jargon Rules

Technical terms are allowed.

Do not avoid real terms like:

- control plane
- runtime manager
- daemon
- telemetry
- observability
- structured output
- RAG
- local inference
- tool registry
- execution engine
- severity
- raw evidence

But define or contextualize them when first introduced.

Bad:

    NeuroCore uses a daemonized runtime manager with a control plane and structured tool contract.

Better:

    NeuroCore runs as a persistent local system instead of a one-off chat session. Internally, that means a daemon, runtime manager, control plane, and structured tool contracts work together to keep system interaction controlled and traceable.

## Page-Type Rules

### Homepage

The homepage should:

- introduce the ecosystem
- explain the core philosophy
- route visitors to deeper pages
- stay concise
- show that the work is real
- link to Projects, Knowledge Base, Story, and approved public proof or artifacts when they exist

The homepage should not:

- explain the entire architecture
- contain full product documentation
- become a Knowledge Base article
- carry every future roadmap idea

---

### Project Pages

Project pages should explain:

- what the project is
- why it exists
- what problem it solves
- how it fits the ecosystem
- current status
- what exists now
- what is planned
- where proof lives

Project pages should not become raw repository docs.

They should translate technical work into public understanding.

---

### Knowledge Base Pages

Knowledge Base pages should:

- teach one useful idea clearly
- be SEO-friendly without keyword stuffing
- use examples from the ecosystem
- link naturally to related project pages
- avoid copying internal architecture docs wholesale

Each article should answer one focused question.

Long-form Knowledge Base articles should use the prose-first reading standard established by the focused AI Operations project-context guide.

That standard means:

- use fuller paragraphs with natural transitions
- avoid making the page feel like a checklist or documentation dump
- use bullets only when they genuinely improve scanning
- avoid long numbered lists unless the article is teaching a sequence
- use two or three strong explanatory diagrams rather than many weak ones
- make diagrams feel like polished article graphics, not code blocks or file trees
- keep FAQ useful but secondary
- preserve current-vs-future boundaries

Examples:

- Why should AI reason but not hold authority?
- What does persistent AI memory actually mean?
- Why is raw command output not enough for diagnostics?
- What is safe AI tool interaction?
- Why does continuity need to be engineered?

---

### Story Pages

Story pages should:

- explain origin and philosophy
- connect human experience to architecture
- support the brand identity
- stay credible and grounded

They should not:

- overshare personal detail
- become melodramatic
- sound like fiction
- replace technical explanation

---

### Build Notes

Build Notes should:

- summarize meaningful development milestones
- explain why the change mattered
- link to approved public technical artifacts where appropriate
- be readable by public technical readers

Build Notes should not:

- replace source build logs
- dump raw implementation details
- pretend every commit is a public milestone

---

### Resources Pages

Resources pages should:

- collect useful links
- route readers to approved public repositories or technical artifacts, videos, future downloads, docs, and demos
- stay practical

They should not:

- advertise unavailable downloads
- imply product readiness before it exists
- duplicate entire project pages

---

## Structure Rules

Use headings to create a clear reading path.

Prefer:

    Clear sections.
    Strong headings.
    Short-to-medium paragraphs with natural transitions.
    Fuller paragraph flow for long-form articles.
    Bullets only when they improve scanning.
    Narrative prose when explaining story, philosophy, or operating method.
    Tables only when comparison is useful.
    A small number of purposeful diagrams when they improve understanding.

Avoid:

    Massive bullet lists replacing explanation.
    Repeated one- or two-sentence fragments that make articles feel disconnected.
    Too many diagrams interrupting the reading path.
    Diagrams that look like terminal output, code blocks, file trees, or internal planning artifacts unless that is the subject.
    Dense technical paragraphs.
    Repeating the same project summary on every page.
    Burying the current status.
    Ending pages without a next step.

---

## Internal Link Style

Link only when it helps the reader.

Prefer linking:

- first meaningful mention of a topic
- project names
- major concepts
- “learn more” transitions
- clear next-step buttons

Avoid:

- linking every repeated mention
- creating dead links
- linking to internal planning docs
- linking to future pages before they exist
- using vague link text like “click here”

Preferred link text:

- Explore NeuroCore
- Read about Argus ACLI
- Learn how the ecosystem fits together
- View the public technical artifact
- Explore the Knowledge Base

## Public vs Internal Language

Public pages must not include internal planning language.

Avoid public phrases like:

- this section should
- future article should
- update this later
- source docs required
- placeholder
- the assistant must
- closeout
- anti-drift rule
- page inventory
- repo map
- content source map
- do not overstate

Those belong in internal docs.

Public pages should say what visitors need to know.

Internal docs can say what builders and AI sessions need to do.

## Claim Safety Rules

Before making a factual project claim, confirm it from source docs.

Do not invent:

- features
- maturity level
- architecture details
- product availability
- install steps
- supported platforms
- commercial plans
- user workflows
- performance claims
- security guarantees
- customer claims
- production readiness

If source docs are missing, ask for them.

If the page is public-facing and the feature is future-phase, label it clearly.

## Phrase Boundaries

Be careful with these phrases:

### “Agent”

Use cautiously.

If used, clarify that TENSA is not building uncontrolled command-launching agents.

Prefer:

    controlled AI system
    governed tool interaction
    model-assisted reasoning
    AI-assisted diagnostics

### “Automation”

Use cautiously.

Argus ACLI V1 is read-only.

Avoid implying automated remediation.

Prefer:

    diagnostic support
    inspection
    structured analysis
    recommendations
    human-directed troubleshooting

### “Memory”

Clarify what memory means.

Avoid implying magical human-like memory.

Prefer:

    engineered continuity
    externalized operational memory
    repository-grounded context
    persistent project understanding

### “Safe”

Do not make absolute safety claims.

Prefer:

    designed around control boundaries
    read-only by design
    governed execution paths
    traceable tool interaction

Avoid:

    completely safe
    risk-free
    secure by default
    impossible to misuse

## Page Review Checklist

Before publishing or replacing a public page, check:

- Does the page explain what exists now?
- Does it clearly label future-phase ideas?
- Does it avoid AI hype?
- Does it avoid corporate fluff?
- Does it avoid internal planning language?
- Does it use source-grounded factual claims?
- Does it explain technical terms clearly?
- Does it route readers to a useful next step?
- Does it avoid duplicating entire technical docs?
- Does it fit the role of that page type?
- Does it preserve the TENSA ecosystem model?
- Does it avoid overstating product maturity?
- Does it sound human, practical, and credible?
