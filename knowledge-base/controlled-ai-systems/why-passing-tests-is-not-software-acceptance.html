Why Passing Tests Isn't Software Acceptance

What Agent Operations learned when coding workers passed their tests, but independent review still found defects that mattered.

Controlled AI Systems Article 2 of 4 · Evidence checkpoint: November 2, 2026

A green test suite is one of the most reassuring things a coding agent can report. It means that some executable checks ran and produced their expected results. It does not necessarily mean that the code meets the original requirements, that the tests covered important failure conditions, or that the implementation is ready to become part of a larger system. Those are different questions, and the difference became impossible to ignore during development of Agent Operations, TENSA Engineering's supervised coding-execution system.

Agent Operations is the execution foundation being developed as part of TENSA Driveline, which aims to connect approved discovery and planning with controlled software implementation. Its early coding experiments were not simply demonstrations that AI could generate programs. They were attempts to understand what evidence is sufficient to accept software produced with limited human supervision. The most useful results included several cases where passing tests were not enough.

The result that changed the acceptance process

During a paired calibration, Claude Code and Codex worked on comparable engineering assignments. Both completed implementation and repair attempts within their assigned workflows. One candidate reached 123 passing tests, while the other reached 182 passing tests. Independent examination still found acceptance-blocking defects in both implementations. The issues included process behavior, execution boundaries, environment-related handling, and gaps in test coverage. The larger passing test count did not rescue a candidate that failed requirements the existing suite did not adequately exercise.

A later Agent Operations component produced another revealing result. Its initial validation passed 254 automated tests, yet independent review identified additional blocking defects. These were not reasons to declare automated testing useless; they showed the need to separate what a test proves from what the operator must ultimately decide. A test is evidence about the conditions it covers. Acceptance is a judgment about whether the candidate satisfies the approved requirements with remaining risk understood.

This distinction becomes more important when the same model writes both the implementation and its tests. The model may faithfully encode a mistaken interpretation of the requirement in two places, producing a consistent but incorrect implementation. It may omit an error path, accept an invalid response, or make assumptions about how a process terminates. The suite can then pass perfectly while leaving the relevant defect undetected. The correct response is not to demand a bigger number of tests without examining what those tests mean.

Validation must describe a particular candidate

Even a carefully designed test suite can be misleading when it is detached from the final code. A worker might run the prescribed tests, make another small change, and then report the earlier result as evidence that the final implementation passed. A reviewer might inspect a committed diff while important untracked files sit outside it. In either case, the report describes something other than the software the operator is considering for acceptance.

Agent Operations responded by treating the candidate's identity as part of the evidence. The current manually supervised foundation includes workspace validation, prescribed command execution, and an artifact inventory that identifies created and changed files. The intended managed review process must connect the starting revision, all relevant workspace changes, test outputs, and review findings to the same candidate. If the software changes after a test or a review, the relevant evidence may need to be refreshed.

An early worker experiment exposed the inventory problem directly: an ordinary Git diff looked empty even though new implementation files existed. That experience helped establish why a complete file inventory matters. A reviewer should not have to infer the entire result from a worker's summary or one convenient view of the repository. Reproducibility starts with being able to say exactly what was built and examined.

The prescribed validation command is also an important boundary. A coding worker may have reasonable ideas for additional checks, but it should not quietly substitute an easier test for the one the task requires. The operator needs to know what ran, where it ran, whether it finished, and which candidate it exercised. A recorded exit code and output have more value than a narrative such as “all checks look good,” although neither can establish that the coverage was sufficient on its own.

Independent review must have an independent job

A review process adds value only if it is able to challenge the builder. Asking the original coding session to rephrase its confidence is not independent review. Asking a second model whether the first model's summary sounds plausible is little better. A reviewer should receive the approved assignment, the actual changes, the relevant test evidence, and enough source context to identify defects the original implementation may have missed.

The managed-worker design therefore gives the reviewer a distinct role. Its intended default is a fresh, read-only model from a different provider family than the builder. That separation does not guarantee correctness, but it reduces the risk of simply repeating the original assumptions. The reviewer reports findings and their evidence; it does not silently rewrite code, approve its own changes, or accept the task on the operator's behalf.

A small October–November 2026 experiment demonstrated a meaningful part of that separation. Claude Code corrected a percentage calculation in a bounded fixture and ran the required focused test. Grok then performed a fresh, read-only review by inspecting the changed file and test. The recorded review showed actual file reads, no observed edits, and a reasoned assessment that identified limitations in test coverage and potential rounding considerations. Grok did not run the test itself, which remains an important limitation of that evidence. The two roles were distinguishable, but this was still a manually arranged experiment rather than an unattended managed-review lifecycle.

This result matters because good review is not a popularity contest between models. If the builder and reviewer disagree, the system must make the disagreement visible and preserve the supporting evidence. Independent review is designed to surface uncertainty and defects before a person accepts the candidate; it does not transfer acceptance authority to whichever model sounds more certain.

Repair cannot become an infinite loop

When a reviewer finds a blocking defect, the candidate may require another implementation pass. This raises a subtle control problem: who decides that the coding worker may modify the work again, and for how long? In Agent Operations, the task packet carries a bounded repair policy. The current manual workflow allows defined repair attempts inside the approved scope and stops when the budget is exhausted or the work would require new authorization.

This makes repair a controlled continuation of the original assignment rather than an open-ended instruction to “keep fixing it until everything is green.” Every repair changes the candidate. The tests must remain meaningful for the new version, and the findings that prompted repair must be examined again. A repair that resolves one defect while introducing another is not acceptance progress merely because the worker has completed another iteration.

There is also a business consequence. Unlimited repair attempts can hide the real cost of an implementation. A result that required repeated model sessions, new test suites, additional reviews, and extensive operator intervention may be more expensive than a simpler approach, even if its final test count looks impressive. The useful unit is accepted software with evidence, not the volume of code or the number of agent turns.

The acceptance decision belongs to the engineer

The planned managed workflow is not intended to replace engineering judgment with a reviewer model's verdict. Validation can establish observed behavior. Independent review can identify defects and remaining risks. The person responsible for the work decides whether the evidence satisfies the task's acceptance criteria and whether any separate integration or delivery action is justified.

This is especially important for a larger system such as TENSA Driveline. Its public project page describes a developing process that begins with discovery and planning, then moves toward supervised implementation. The current foundation has demonstrated bounded work, validation, independent technical review, and accepted components, but it has not demonstrated a complete unattended, multi-project acceptance and delivery service. The distinction between established steps and the intended integrated pipeline is part of the project's engineering honesty.

The lesson from 123, 182, and 254 passing tests is not that those tests failed to matter. They were necessary evidence, and they helped expose where the testing strategy itself was incomplete. The mistake would have been treating an impressive count as a substitute for understanding the tested candidate, its requirements, and the unresolved defects. A system becomes more trustworthy when it can report that distinction clearly, including when the correct outcome is rejection.
